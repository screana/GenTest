# 決定ログ

「何を考え、なぜそうしたか」を残す。新しいものを下に追記する。

## 2026-10-20

### D-01 想定シナリオ：単体テスト自動化の依頼
- 決定：顧客からサンプル設計書とコードを受領し、テスト仕様書の生成、テストスクリプトの設計・実行までを行う
- 理由：コードを実行できると、カバレッジや仕込みバグの検出率といった客観的な数字で品質を示せる

### D-02 言語は Python、LLM は Gemini
- 決定：pytest、Gemini（Vertex AI）を使う
- 理由：既存の環境（mock/）でそのまま始められる

### D-03 題材は jpholiday
- 決定：OSS の jpholiday（MIT）を対象にする
- 理由
  - 祝日法という、コードとは独立した公開仕様がある。設計書をコードから書くと設計書がコードの写しになり、不具合を見つけられない構造になる
  - ハッピーマンデー、法改正による適用期間、特例年、振替休日・国民の休日の依存関係など、境界条件が多い
  - 既存テストがあり、人が書いたテストと比較できる
- 注意：有名な OSS のため、LLM が既存テストを記憶している可能性がある。既存テストとの類似度を参考値として記録する

### D-04 期待値は設計書から取る。LLM による期待値の書き換えを仕組みで防ぐ
- 決定：テストスクリプトは期待値を持たず、仕様書 JSON から読み込む
- 理由：失敗したテストを LLM に直させると、期待値をコードに合わせてしまい、バグを見逃すテストになる。プロンプトで禁止するより、構造で防ぐほうが確実

### D-05 Skills / Hooks の考え方をパイプラインで実装する
- 決定：観点チェックリストを外部ファイル化する（Skills 相当）。生成後に機械的に検証して再生成する（Hooks 相当）
- 理由：Gemini をパイプラインから呼ぶ構成ではそのまま使えない。また、条件を自分で制御できるので、効果を比較実験で示せる

### D-06 仕込みバグは1バージョンに1つ
- 決定：観点ごとに多種類のバグを用意し、1バージョンに1つだけ入れる。LLM には見せない
- 理由：どのバグをどのテストが検出したかを1対1で追えるようにするため

### D-07 設計書は、コードを見ないサブエージェントに書かせる
- 決定：jpholiday の実装・テストを読まないという制約を付けたサブエージェント（Claude）に、祝日法・内閣府・国立天文台の一次情報だけから詳細設計書を書かせる。インタフェースの確認のため、README だけは読んでよいことにする
- 理由：メインの作業者（Claude）はすでに実装の概要を読んでいるため、自分で書くとコードに引っ張られる。文脈を引き継がないエージェントに任せることで、設計書がコードから独立していると説明できる
- 補足：法律にも README にも根拠がない挙動（期間の端点、例外など）は推測で決めず、「未定義事項」として明示させる。これらはテストの期待値にできないので、仕様書生成でも扱いを決める必要がある

### D-08 LLM の呼び出し回数を抑える
- 決定：LLM の応答をキャッシュし、開発中は保存済みの応答で動作を確認する。本番の実験は、呼び出し回数を見積もってから実行する
- 理由：API の利用料がかかるため

## 2026-10-22

### D-09 未定義事項は「顧客確認待ち」として仕様書に出力する
- 決定：設計書 9章の未定義事項に当たるケースは、仕様書から除外しない。期待値を持たない「確認待ち」の区分で出力する
- 理由：実際の案件では顧客への確認事項になる。また、LLM が根拠のない期待値を作らなかったかを評価できる
- 懸念：区分の使い方を例示しないと、LLM がほとんどのケースを確認待ちにするおそれがある。Few-shot で「期待値あり」と「確認待ち」の両方の例を与える

### D-10 仕様書の生成とスクリプトの生成で、LLM に渡すものを分ける
- 決定：仕様書を生成するときは設計書だけを渡す。スクリプトを生成するときだけコード（公開インタフェース）を渡す
- 理由：仕様書の段階でコードを見せると、期待値がコードの挙動に引っ張られる

### D-11 既存テストとの比較はテスト設計の分析として行う（D-03 の注意を具体化）
- 決定：既存テストと生成テストを、観点ごとのケース数、テストしている年・日付、仕込みバグの検出率で比べる。テキストの類似度は測らない
- 理由：比べたいのはテスト設計の違いである。記憶の再現かどうかも、この分析の中で確かめられる
- 記憶の確認：既存テストが年ごとに網羅しているのは 1971, 1988, 1989, 1992, 1997〜2027 で、法改正の境界とは関係がない。生成テストが選んだ年がこの並びとよく一致すれば、既存テストを記憶している疑いがある

### D-12 パイプラインは関数呼び出し（エージェント）ではなく、固定のワークフローで作る
- 決定：Gemini の関数呼び出しは使わない。「構造化出力で生成 → 機械的に検証 → 指摘を付けて不合格の項目だけ直させる」というループを、コードで固定の手順として書く
- 理由：段階の流れが決まっているので、エージェントにする必要がない。ツールを提出用に使っても、やっていることは同じループで、呼び出し回数の管理とデバッグの手間が増えるだけである
- 補足：「必ず守らせたいことはコードで強制する」「構造化エラーを返して直させる」「推測させないスキーマにする」といった原則は、このループとスキーマで実現する

### D-13 ID はコードで振る
- 決定：REQ-ID と TC-ID は LLM の出力をそのまま使わず、生成した直後にコードで連番を振り直す
- 理由：重複や欠番を LLM に直させる意味がない。機械的に決まることは機械で決める

### D-14 章ごとに生成する
- 決定：要件の抽出と仕様書の生成を、設計書の章ごとに行う。各呼び出しには設計書の全文を渡し、対象の章を指定する
- 理由：一度に全体を生成すると出力が長くなり、途中で切れたり後半の質が落ちたりする。章をまたぐ参照（例：5.4 が 7章を参照する）があるので、全文は毎回渡す

### D-15 コードと LLM の役割（D-10 を変更）
- 決定
  - LLM が pytest スクリプトを生成する。期待値は spec.json から読み、スクリプトに期待値を直接書くことは静的な検査で禁止する
  - LLM がコードを読み、通っていない分岐を通す入力を追加で提案する
- 理由：目的は「設計書とコードから、LLM で仕様書とスクリプトを生成する」ことである。レビューで、コードが入力としてどこにも使われていないこと、スクリプト生成に LLM の役割がないことを指摘された
- D-10 からの変更：D-10 はコードを渡すのをスクリプト生成のときだけとしていたが、入力を提案する段にも渡す。渡すものは段ごとに次のとおりとする
  - 仕様書の生成（期待値を決める段）：設計書だけ。コードは渡さない（D-10 のまま）
  - スクリプトの生成：公開関数のシグネチャと docstring（functions.py）、spec.json のスキーマ
  - 入力を提案する段：target/ のコード全体と、カバレッジの未到達箇所
- 守ること
  - コードを読む段は、入力だけを出す（スキーマに期待値の欄を作らない）。期待値は、設計書と入力だけを渡す仕様書生成の段で決める。根拠がなければ確認待ちにする（D-09、D-10）
  - 各ケースに由来（設計書から／コードから）を記録する
  - コードの読み取りとスクリプトの生成は、元のコードで一度だけ行って固定する。バグ版のコードは LLM に見せない（D-06）
  - スクリプトの修正ループに渡すのは、収集エラーと import エラーだけにする。期待値が合わずに落ちたテストを LLM に直させると、D-04 で防いだ「テストをコードに合わせる」抜け道がスクリプトの側で復活する
- 限界：コードに分岐がない種類のバグ（実装漏れ）は、コードを読んでも見つからない。これは設計書から作るケースが受け持つ

### D-16 テストの対象は公開関数とし、内部クラスはカバレッジで見る
- 決定：テストケースは設計書 8章の公開5関数に対して作る。内部のクラス（祝日ごとの Checker など）はテストの対象にせず、カバレッジ（行・分岐）で通したかを測る
- 理由：期待値の根拠になるテストベースは設計書で、設計書が定めているのは公開関数の振る舞いだけである。クラスごとにテストを作ると期待値をコードから取ることになり、コードの誤りを正しいと確かめるテストになる
- 補足：仕様から作るケース（ブラックボックス）と、カバレッジによる網羅の確認（ホワイトボックス）を組み合わせる。D-15 のコードを読む段は、通っていない分岐を通す役になる

### D-17 設計書の不明点・矛盾は QA票で顧客役に確認する
- 決定：パイプラインは、確認待ちのケースと設計書の矛盾を、解釈案を添えた質問の形で QA票にまとめ、顧客役のサブエージェントが回答する。回答を反映した仕様書を2周目として作る
- 理由：テストベースを決めるのは顧客であり、受託側が設計書を勝手に直すことはない。実務の流れ（質疑 → 回答 → 反映）を再現できる。設計書の既知の矛盾（7.4 と 9.1.6、3.15.2 と 9.1.5、5.5 と 9.1.4）を LLM が質問として挙げられたかは、評価の指標にもなる
- 回答の作り方（実験としてはこの形で固定する）
  - 顧客役は呼ぶたびにまっさらな状態から答えるので、聞き直すと回答が変わる。そのため、回答は実行のたびに作らず、ファイルとして固定する
  - 先に回答集を作る：9章の全項目と既知の矛盾について、パイプラインが質問を出す前に、顧客役にまとめて答えさせる。パイプラインの QA票は、この回答集と照らし合わせる
  - 回答集にない質問が来たときだけ、顧客役に追加で答えさせ、回答集に追記する。追記には版を付ける
  - 顧客役に渡す指示（プロンプト）と回答集はリポジトリに置き、だれが実行しても同じ手順・同じ回答になるようにする
- 顧客役の条件
  - 文脈を引き継がない新しいサブエージェントを使う（D-07 と同じ）。コード、生成したテスト、実行結果、仕込みバグの一覧、メインとのやり取りは渡さない
  - 根拠は公開情報（法令・内閣府・国立天文台）を優先する。根拠がない事項（引数の型など）は、理由を添えて顧客として判断してよい。「対象外」と答えてもよい
  - 限界：Claude が jpholiday を記憶している可能性は残る（D-07 と同じ）
- 質問の書き方：仕様の言葉だけで書く。実装の戻り値など、コードから得た情報を質問や解釈案に入れない（入れると顧客役にコードを見せたのと同じになる）
- 実装との差異は QA票に入れない。実務と同じく不具合票として分ける
- 2周目
  - 回答は、設計書の改訂版に「質疑応答」の章として足す。根拠の引用文は今の照合（validate.py）でそのまま検証できる
  - 作り直すのは、回答に関係するケースだけにする。全部を作り直すと、回答を反映した効果と生成のばらつきが区別できない
- 見送り：仮定を置いて期待値を書き、回答を待たずに進めるやり方は入れない。根拠のない期待値が仕様書に混ざるため。顧客役が答えるので、なくても流れは再現できる

### D-18 評価の指標を4つに絞る
- 決定：まず次の4つを測る
  1. バグ検出率：元のコードで合格し、バグ版で不合格になったバグの割合
  2. カバレッジ：内部クラスを含めた行・分岐
  3. スクリプトの実行可能率：spec.json の確定ケースのうち、テストとして収集され、エラーなく実行まで進んだ割合。期待値が合わずに落ちたテストは「実行できた」に含める（落ちたかどうかは指標1と記録で見る）
  4. 確認事項の検出：設計書の既知の矛盾のうち、QA票に挙がった数。既知の3件以外に見つかったものは別に数える
- 理由：指標を増やしすぎると、計測の仕組みを作ること自体が目的になる。実験条件どうしの比較は第2段階で行う（D-20）
- 補足：バグ検出の定義に「元のコードで合格」を入れるのは、元のコードがすでに設計書と食い違っているため（例：1948-01-01 が「元日」になる）。この条件がないと検出率が水増しされる
- 指標と一緒に必ず残す記録
  - 元のコードで落ちたテストと、その仕分け（実装の誤り／仕様書の誤り／確認待ち）。これがないと、LLM が期待値を間違えたテストは検出率の計算から静かに外れるだけで、誤りとして表に出ない
  - ケース数（検出率は件数が増えるほど上がるため、並べて報告する）
- 基準値：既存テスト（baseline_tests）を同じバグ版で実行し、指標1・2の基準値にする。D-11 の既存テストとの比較もこれで行う
- カバレッジは「設計書から作ったケースだけ」と「全部」の2つを出す。D-15 のコードを読む段に効果があったかを示す証拠になる
- 指標4の注意：既知の3件は、メインもレビュー役も中身を知っている。この3件を意識してプロンプトを直すことはしない（答えを教えることになるため）

### D-19 パイプラインの段の順序
- 決定：次の順に進める
  1. 仕様書の生成（設計書だけから。D-10）
  2. スクリプトの生成（D-15）
  3. 元のコードで実行し、カバレッジを測る。落ちたテストを仕分ける（D-18）
  4. 入力を提案する段（コードとカバレッジの未到達箇所から。D-15）
  5. 提案された入力の期待値を決める段（設計書だけから。1と同じ仕組み）
  6. 再実行（元のコード・バグ版・既存テスト）
- 理由：4 は「通っていない分岐」を知る必要があるので 3 の後になる。2 のスクリプトは spec.json を実行時に読む作りにして、5 で増えたケースも作り直さずに動くようにする

### D-20 実験条件の比較は第2段階にする（D-05 を変更）
- 決定：D-05 のチェックリストや検証の有無による比較実験は、全工程が一周してから第2段階として行う。generate.py の `--no-checklist` と `--repair-rounds` はそのために残す
- 理由：まず全工程をつなげないと、比較の効果をバグ検出率で測れない
